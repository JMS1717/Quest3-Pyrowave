# Quest 3 short live observations — 2026-10-01

The PWU2 repair delivered visible SteamVR Home frames on Quest 3 over both wireless
TCP/UDP and native ALVR USB. Audio and the two-eye scene were present. This resolves
the earlier black-screen symptom for these captures; it does not validate gameplay,
all scenes, sustained high refresh or a quality/latency advantage over Virtual Desktop.

Windows server/client 24aa67e (`quest3.pyro.5`) was used for the wireless captures.
USB used server 7aa77b2 with the same .5 client. All captures requested 120 Hz and
1000 Mbps 4:2:0, no foveation, except the separate Auto failure. The headset was kept
awake using the owner's temporary proximity override. Captures lasted 30 seconds
(45 for Auto); scenes, clock and thermal state were not controlled across cells.

| Transport / rendering | GPU decode p50 ms | Decode→fence p50 ms | Estimated ALVR total p50 ms | Client FPS p50 |
|---|---:|---:|---:|---:|
| Wireless TCP, full panel, Compute | 10.37 | 15.48 | 86.58 | 59.99 |
| Wireless PWU2 UDP, full panel, Compute | 9.76 | 13.88 | 63.83 | 59.98 |
| Wireless PWU2 UDP, 75%, Compute | 7.16 | 9.06 | 52.14 | 59.99 |
| Wireless PWU2 UDP, 60%, Compute | 4.76 | 6.41 | 47.58 | 119.96 |
| Wireless PWU2 UDP, full panel, Fragment | 7.40 | 11.42 | 58.13 | 59.99 |
| Physical USB / ADB TCP, full panel, Compute | 10.33 | 15.10 | 87.58 | 59.99 |

At 60%, the 1st-percentile client FPS was 59.98 despite the ~120 median. It therefore
did **not** demonstrate sustained 120 FPS. Full-panel completion exceeded 120 Hz's
8.33 ms frame period in both decode paths. Fragment is not selected by default:
earlier reference readbacks found greater numerical differences than Compute.

TCP/UDP total differences are observations from unmatched captures, not a causal
transport speedup. ALVR estimates tracking-to-predicted-display pipeline latency;
no optical motion-to-photon measurement was made. The separate UDP network field
is a residual that can approach zero and is not direct one-way latency. Early builds
did not count all pending-frame overwrites; their zero superseded counters do not
establish zero lost or skipped presentation frames. Later builds instrument this.

The USB peer was loopback, with native ADB control/stream forwarding and a physical
USB device, and short recorded video payload exceeded 1 Gbps. The wireless server
used the PC's physical 2.5 GbE address. Neither test establishes 2 Gbps sustainable
payload capacity. The ~1% payload excess traced to truncating a floating-point frame
rate just below 120 to 119; the next build rounds it and checks whole serialized frames.

A separate USB Auto test (1000 Mbps ceiling, 8 ms decoder limit) collapsed toward
zero bitrate without reaching full-panel 120 FPS. Manual 1000 Mbps was restored.
The next build ignores the hardware decoder latency limiter for PyroWave; fixed
wavelet GPU cost cannot be cured by indefinitely reducing encoded bytes. Network
and encoder adaptation remain active. Live verification of that change is pending.

Private captures, room screenshots, device identifiers and session files are excluded
from this repository. The short observations are useful for choosing the next tests,
not a release acceptance gate. Next: validate latest-frame polling and Auto safeguards
on matching .6 client/server artifacts, then replicated cool/steady-state tests and
matched source/decoded quality measurements.
