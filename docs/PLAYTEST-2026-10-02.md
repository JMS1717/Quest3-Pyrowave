# October 2 manual playtest and setup repairs

The owner reported positive visual feedback after the manual PCVR setup and
OpenXR launch repair. This is qualitative feedback from one session; it does not
establish sustained fresh 120 FPS, optical motion-to-photon latency or a win over
Virtual Desktop.

## Matching development build

The session used matching `.29` APK/server artifacts from
[source b0c9753](https://github.com/JMS1717/Quest3-Pyrowave/commit/b0c9753ce5d0b04d8df24f4187f9e03d4abdc358),
with the full cloud build/regression suite passing
[run 37052671109](https://github.com/JMS1717/Quest3-Pyrowave/actions/runs/37052671109).
Hashes, APK certificate, embedded versions and packaged native libraries were
reviewed before installation. This is an Actions development pair, not a new
published release. Alpha.7 still contains matching `.15` binaries.

The `.29` early ready-fence experiment stayed **off**. Its corrected native GPU
probe and controlled ON/OFF comparison remain pending; the manual session does
not validate that synchronization experiment.

SteamVR global resolution was set to 100%; per-game settings were left alone.
SteamVR reported a scaled recommendation of 3280x3448 in this setup. That is not
proof of every game's submitted texture size. Reopen games that cache render
targets after changing the recommendation. The larger PC source and mild
sharpening are optional, not changes to the repository baseline.

## Fixes that mattered

- A leftover `debug.q3pw.overlay_visible=1` benchmark override prevented the
  thumbstick chord from hiding the panel. Clearing it restores normal control
  without an APK update. Manual launchers must leave it unset.
- The larger PC render recommendation was already active. Keeping Quest decode
  fixed limits transmitted detail; modest existing PC sharpening was enabled
  with neutral colors for edge clarity. Its added GPU pass has no controlled
  performance or image-quality acceptance yet.
- Pavlov selected VDXR and reported `XR_ERROR_FORM_FACTOR_UNAVAILABLE`. Selecting
  SteamVR as the Windows OpenXR runtime fixed the route; VD's driver and service
  were preserved. [Check, switch and restore](OPENXR.md).
- Sleep/session teardown could restore 72 Hz after an app stop. Wait for teardown
  before an explicit refresh request, then verify OpenXR frequency and frame
  period. The property alone is not capability or sustained-frame evidence.

## Why 2000 Mbps was not kept

Sequential five-second idle/Home checks at the same render/encode geometry and
confirmed 120 Hz, before PC sharpening was enabled, produced these median ALVR
statistics:

| Target Mbps | Actual payload Mbps | Client cadence FPS | Estimated total pipeline ms |
| ---: | ---: | ---: | ---: |
| 1000 | 1001.91 | 120.00 | 47.13 |
| 2000 | 2010.92 | 120.00 | 58.14 |

The connection carried approximately 2 Gbps briefly, but estimated latency rose
by about 11 ms. **1000 Mbps was restored.** This was a quick usability screen,
not a controlled source-covered game benchmark or sustained USB capacity test.
Clocks and thermals were not held constant, order was not reversed, and client
cadence does not count delivered fresh frames. No FPS gain can be inferred.
An earlier check at actual 72 Hz is excluded from this comparison.
